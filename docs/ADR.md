# 결정 기록 (Architecture & Course Decision Records)

## 철학
교육 원리는 오래 가고 제품 정보는 자주 바뀐다. 둘을 분리하고, 모든 수치와 출처는 한 곳에만 두며, 사람이 검토하지 않은 콘텐츠는 배포하지 않는다. 작동하는 가장 단순한 선택을 한다.

정보 우선순위: 사용자 결정 > 제안서 PDF > 공식 최신 문서 > 기타.

---

## A. 기술 결정 (ADR)

### ADR-001: 정적 사이트 — Astro + MDX + Content Collections [PROVISIONAL]
**결정**: Astro 정적 출력. 교시는 MDX, frontmatter는 zod 스키마.
**이유**: 페이지당 JS가 거의 없고, Markdown으로 강사가 직접 수정 가능하며, frontmatter 누락을 빌드에서 막는다. Vercel이 자동 인식한다.
**트레이드오프**: Next.js 대비 동적 기능이 약하다(필요 없음). 순수 HTML 대비 빌드 도구가 필요하다. 버전은 Phase 1에서 공식 문서로 확정.

### ADR-002: 서버·DB·로그인·분석 도구 없음
**결정**: 진행 체크는 브라우저 localStorage만 쓴다. 쿠키·분석 스크립트를 넣지 않는다.
**이유**: 교육자료 제공에 필요 없고, 공공기관 교육에서 개인정보 수집 논란을 원천 차단한다.
**트레이드오프**: 수강생 진도를 강사가 볼 수 없다(상호평가는 구글 폼으로 대체).

### ADR-003: 데이터 단일 원천
**결정**: 구조·수치는 `content/course.yaml`, 제품 정보·출처·외부 링크·용어·금지 표현은 각 등록부 yaml에만 둔다. docs는 설계 근거만 쓴다.
**이유**: 같은 정보가 여러 곳에 있으면 시간이 지나며 어긋난다. validator가 원천을 기준으로 검사할 수 있다.
**트레이드오프**: 문서만 읽어서는 수치를 알 수 없다(course.yaml을 함께 본다).

### ADR-004: 검사 담당 분리 — 등록부는 Python, MDX는 zod
**결정**: 등록부 yaml과 교차 규칙은 `scripts/validate_course.py`, MDX frontmatter는 zod가 검사한다. 같은 규칙을 두 곳에 구현하지 않는다.
**이유**: Phase 0부터 검사가 필요하고(Astro 이전), 규칙 이중화는 불일치를 만든다.
**트레이드오프**: Vercel 빌드는 Python 검사를 돌리지 않는다 → ADR-007의 CI로 보완.

### ADR-005: 사람 검토 관문과 해시
**결정**: 콘텐츠 status는 planned → draft → reviewed. AI는 draft까지만. 사람이 `review:approve`로 승인하면 `reviewed_hash`를 기록하고, 이후 본문이 바뀌면 오류로 처리한다. Production은 core 전부 reviewed일 때만.
**이유**: 법령 해석과 교육 적합성은 자동 검사로 보장할 수 없다. 승인 후 수정이 검토를 우회하지 못하게 한다.
**트레이드오프**: 사람 검토가 병목이 된다 → 콘텐츠 phase마다 human-review step을 두어 분산한다.

### ADR-006: Harness 실행기 개편 (execute.py)
**결정**: UTF-8 입출력, stdin 프롬프트 전달, core 문서(CLAUDE.md·PRD·ARCHITECTURE·ADR·CONTENT_GUIDE) 고정 + phase별 `guardrail_docs`, `depends_on`(main 병합 기준), phase 요약 전달, `allowed_paths` 검사, `HARNESS_EXECUTING=1`.
**이유**: Windows 한글 인코딩과 명령줄 길이 한계, docs 증가에 따른 프롬프트 비대화, phase 간 의존과 범위 이탈을 막기 위해.
**트레이드오프**: step 설계 시 allowed_paths와 guardrail_docs를 적어야 한다.

### ADR-007: 브랜치와 배포 — phase 브랜치 → PR → CI → main = Production
**결정**: phase는 한 번에 하나씩, `feat-<phase>` 브랜치에서 실행하고 PR로 main에 병합한다. GitHub Actions에서 `npm run verify`를 돌리고 main을 보호한다. 웹 편집도 새 브랜치 → PR로만 반영한다. Phase 0은 로컬 `feat-0-foundation` 브랜치.
**이유**: Vercel Preview로 확인한 것만 Production에 가게 하고, Python 검사를 CI에서 강제한다.
**트레이드오프**: 작은 수정도 PR을 거친다.

### ADR-008: 오프라인 번들과 인라인 스크립트
**결정**: `build:offline`으로 상대경로 정적 폴더를 만든다. 인터랙션 스크립트는 인라인 비모듈, 외부 CDN·웹폰트 금지.
**이유**: 교육망이 Vercel을 막을 수 있고(CD-05), Chrome은 file://에서 모듈 스크립트를 차단한다.
**트레이드오프**: 스크립트 번들 최적화를 포기한다(스크립트가 작아 영향 적음).

### ADR-009: Public 저장소의 공개 범위
**결정**: `references/`(원본 PDF)는 커밋하지 않는다. 강사 민감 메모는 저장소 밖에 둔다. 원작자 허락(CD-15) 전에는 push하지 않는다. 콘텐츠 라이선스는 허락 후 정한다 [TBD: OQ-13].
**이유**: 원본 PDF에 내부 운영 메모와 인적사항이 있고, 원본 프레임워크에 라이선스가 없다.
**트레이드오프**: 허락 전에는 CI·Preview를 쓸 수 없어 로컬 검증으로 대체한다.

### ADR-010: 호스팅 요금제 [PROVISIONAL]
**결정**: Vercel을 유지하되, Hobby 요금제는 비상업 용도만 허용하므로 유료 강의 운영에는 Pro 요금제 또는 대안 호스팅을 검토한다 [AS-OF: vercel-hobby-commercial] [TBD: OQ-09].
**이유**: 사용자 요구는 Vercel 배포이나, 약관상 강의 수익과 연결된 배포는 상업적 사용으로 볼 수 있다.
**트레이드오프**: Production 공개 전에 결정해야 한다(Phase 0~7 제작은 막지 않음).
