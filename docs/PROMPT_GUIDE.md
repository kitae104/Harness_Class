# AI에게 도움받기 카드(Prompt Card) 가이드

카드는 **막히는 곳에서 수강생이 AI와 함께 하네스를 설계하도록 돕는 도구**다. 정답을 대신 만드는 답안이 아니다. 카드 목록과 배치는 course.yaml `cards`와 `stuck_points`가 원천이다.

## 1. 카드를 만들 조건
- course.yaml에 **막힘 지점(stuck_point)** 이 먼저 있고, 그 지원 방식에 카드(1·2·8)가 필요할 때만 만든다(V-CRS-008).
- 교시당 2장 이하 권장(V-CRS-011). 전체 core 카드 상한은 constraints.
- 프롬프트 라이브러리를 채우기 위해 카드를 만들지 않는다. 라이브러리는 실제 쓰이는 카드만 보여 준다.

## 2. 카드 파일 스키마 (`content/prompts/<id>.md`, Phase 1에서 zod로 강제)
| 필드 | 내용 |
|---|---|
| `id` | course.yaml `cards[].id`와 같음. 분류 문자를 넣지 않는다(분류가 바뀌어도 ID 유지) |
| `stuck_point` | 근거가 되는 막힘 지점 ID |
| `where` | 붙여넣을 곳: `instructions`(지침란) / `project-chat`(Project 채팅) / `new-chat`(새 채팅) / `temporary-chat`(임시 채팅) |
| `when` | 언제 사용하는가 |
| `input` | 무엇을 입력해야 하는가 |
| `l3_structure` | 직접 쓰기 단계: 5칸 뼈대만 |
| `l2_template` | 바꿔 쓰기 단계: 대괄호 부분만 바꾸는 프롬프트 |
| `l1_full` | 따라 쓰기 단계: 그대로 복사하는 프롬프트(예시 값 포함) |
| `default_level` | 교시에서 기본으로 보여 줄 단계(course.yaml `cards[].level`) |
| `line_notes` | 문장별 해설: 어떤 요소(①~⑥)이고 왜 필요한가 |
| `replace` | 사용자가 바꿀 부분(대괄호 목록과 일치해야 함) |
| `check` | 결과에서 확인할 것 |
| `do_not_trust` | 그대로 믿으면 안 되는 부분 |
| `next` | 다음 행동 |
| `tested_at`, `tested_by` | 실제 Plus 계정에서 테스트한 날짜와 사람 |

카드의 검토 상태(`status`, `reviewed_hash`)는 카드 파일이 아니라 course.yaml `cards[]`에 있다(ADR-011).

사용자 요구의 7개 필수 항목(언제 / 무엇을 입력 / 복사할 프롬프트 / 바꿀 부분 / 확인할 것 / 믿으면 안 되는 부분 / 다음 행동)은 `when`, `input`, `l1_full`·`l2_template`, `replace`, `check`, `do_not_trust`, `next`로 모두 들어 있다.

## 3. 5칸 뼈대 — 모든 카드 공통
지침서 5항목과 같은 구조다. 수강생은 카드를 쓰면서 같은 뼈대를 반복해서 보고, 직접 쓰기 단계에서는 이 뼈대만 받는다.
```
[역할]      너는 ○○ 업무를 돕는 ○○다.
[입력]      아래는 [내가 넣는 자료]다.
[규칙]      반드시 지킬 것 / 하지 말 것
[출력 형식] 이런 모양으로 답하라.
[모를 때]   모르는 정보는 지어내지 말고 "확인 필요"라고 표시하라.
```
모든 카드에 "모르는 정보는 '확인 필요'" 문장과 "실제 개인정보를 넣지 마세요" 안내를 넣는다.

## 4. 작성 원칙
1. **먼저 스스로, 그다음 AI**: 설계형 카드(지침, 평가 문항, 업무 분석)는 "직접 쓴 것을 붙여 넣고 빠진 것·애매한 것을 비판받기" 형태로 만든다.
2. **대괄호 표기**: 바꿀 부분은 `[내 업무를 입력]`처럼 대괄호로 쓰고 `replace` 목록과 1:1로 맞춘다(Phase 1에서 V-PRM 규칙으로 검사).
3. **붙여넣을 곳을 명확히**: 지침란에 넣는 "지침 조각"과 채팅에 넣는 "요청"을 섞지 않는다.
4. **길이**: 반복되는 규칙은 카드에 계속 붙이지 말고 Project 지침으로 옮기라고 `next`에 안내한다.
5. **제품 정보 없음**: 카드 안에 모델명·메뉴 위치·한도를 쓰지 않는다.

## 5. 나쁜 카드 (만들지 않는다)
| 나쁜 카드 | 이유 |
|---|---|
| "평가 질문 10개 만들어 줘" | 수강생이 생각할 부분을 대신한다 → "내가 쓴 3개를 비판해 줘"로 |
| 실제 이름·연락처를 입력하게 하는 카드 | 개인정보 입력을 가르친다 |
| "확인 필요" 지시가 없는 카드 | 근거 없는 답을 허용한다 |
| 교시마다 비슷한 긴 규칙을 반복하는 카드 | "긴 프롬프트 = 하네스" 오해를 만든다 |
| 결과 확인(`check`)이 없는 따라 쓰기 카드 | 복사만 하고 판단하지 않게 만든다 |
| 답변 단계에 기대 답변을 넣는 평가 카드, Project 안에서 채점하는 카드 | 점수가 부풀고 프로젝트 메모리로 재평가가 오염된다 → 답변은 질문만, 채점은 Project 밖(PRACTICE_DESIGN 3절, CD-17) |

## 6. 실제 테스트 절차 (사람 검토 항목)
1. 교육용 Plus 계정에서 카드의 `where`에 맞는 곳에 `l1_full`을 붙여 실행한다.
2. `check` 항목으로 결과를 판정하고, `do_not_trust`에 적은 위험이 실제로 나타나는지 본다.
3. 결과 요약을 테스트 기록 양식(QUALITY_CHECKLIST)에 적고 `tested_at`, `tested_by`를 채운다.
4. `tested_at`이 constraints.freshness_days를 넘으면 개설 전 다시 테스트한다.

## 7. 분류 (A~I, 라이브러리 필터용)
| 분류 | 내용 |
|---|---|
| A | 이해하기, 공통 문제 해결 |
| B | 업무 분석, 업무 처리 흐름(분류·초안) |
| C | 지침(Instructions) |
| D | 근거(Context) |
| E | 검증(Evals) |
| F | 안전장치(Guardrails) |
| G | 기록(Observability) |
| H | 내 업무 프로젝트 |
| I | 선택: Codex |
분류 I 카드는 track이 optional이어야 하고 core 교시에 배치할 수 없다(V-CRS-009).

## 8. 제안서 프롬프트 ①②③ 이관
| 제안서 | 카드 | 바꾼 점 |
|---|---|---|
| ① 응답 일괄 분류·요약 | `card-classify-attachment` | 붙여넣기 → 채팅 첨부(CD-07), 붙여넣기는 플랜 B로 `next`에 안내 |
| ② 건별 답변·보고서 초안 | `card-draft-replies` | 5건으로 제한, 검토 열 안내 추가 |
| ③ 평가·채점 | `card-batch-grading` | 채점 기준을 CD-06(문항당 1점, 자료 없음 문항 규칙)으로 수정. **채점 전용**으로 바꿔 Project 밖 임시 채팅에서 쓴다. 답변은 질문만 넣어 따로 받는다(CD-17) |
